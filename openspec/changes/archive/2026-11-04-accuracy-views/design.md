## Goals / Non-Goals

**Goals:**
- Tray reads, meal links and meal outcomes follow the read log's existing rules, with no new table, no new link column and no extra model or HTTP request.
- One scoring module for every class table, portion and volume score, used by the ward summary and by the tray eval.
- Views that show both sides of every classification: kept against not kept for positives, confirmed against overridden for negatives, with counts on every rate.
- Charts that are correct by construction, using the dataviz method: form first, colour validated by script, thin marks, a legend, and a table view.
- No bundle growth on first paint: the bars and the hospital section load lazily.

**Non-Goals:**
- Container or fluid-kind truth in the ward, dish names, and per-fluid kinds in the ward (proposal, Out of scope).
- Marking retaken photo reads. They keep read-outcomes' rules, since a second photo on the same bed within 10 minutes may be a different container (proposal, Out of scope).
- A new tray eval. tray-comparison owns it; this change aligns its scoring with the ward (§9).
- Dark mode, trends, per-staff or per-ward comparisons.

## Types (`packages/shared`)


`MealReadResult` is not changed: the pipeline keeps returning it, and the route returns `Logged<MealReadResult>`. `ReadMode` already holds `sam+spark` and `spark`, which are the tray modes too. `Meal` is not changed: meals do not return their `read_id`, so no meal fixture changes. `ReadKind` gaining `tray` makes the web's `KIND_LABEL` and read-outcomes' link-kind table exhaustive over it.

## Decisions

### 1. Tray reads in the log (`src/routes/ai.ts`, HTTP; `src/ai/read-log.ts`, domain)

- The `/meal` handler calls `store.recordRead(readRow('tray', result, { staffId, admissionId }))` after the pipeline returns, and answers `{ ...result, read_id }`. A thrown pipeline error, a budget refusal (acuity-budget's 429 `request_budget_exceeded`, "Refused by the budget"), a 404 for an unknown bed or a 400 for `meal` without a bed stores nothing. The handler is already `Hono<Env>` (read-outcomes), and `admission_id` is already parsed and checked by tray-comparison's "Tray reads name their bed". It is passed to `readRow` only.
- "Tray reading" stays tray-comparison's text, except "It saves nothing." → "It saves only its read." `read_id` is stated in "Tray reads are logged", so "Tray reading" keeps its own scenarios, with "Half-eaten lunch" saying no meal or entry is saved.
- **The `tray` arm of `ReadOutput`**, closed-list values and numbers only:

  ```ts
  interface TrayDishFacts { index: number; dish_kind: DishKind; portion: Portion; basis: PortionBasis }
  type ReadOutput =
    | /* …read-outcomes' photo and note arms… */
    | { kind: 'tray'; served: boolean; portion: Portion
        dishes: TrayDishFacts[]
        fluids: { index: number; fluid_kind: MealFluidKind; volume_ml: number }[]
        draft: { portion: Portion; fluid_ml: number | null; dishes: { dish_kind: DishKind; portion: Portion }[] } | null }
  ```

  - `served` is `result.comparison !== null` (a served photo was found, whether or not its SAM ran).
  - `drafts` is `trayDrafts(result.draft)`, and `draft` is null when it is 0 (no dish and `fluid_ml` null), as for a `not_a_meal` or `tray_empty_unclear` read that read nothing.
  - `confidence` comes from `reading.confidence`, `issues` from `reading.issues` (parsed with `z.enum(MEAL_ISSUES)`), `hint` is null, and `models` is the distinct trace models in call order.
  - **Never copied:** dish and fluid `name`, `items`, `notes`, `box`, `coverage`, `measure`, masks, `segmentation`, `comparison` (it holds `served_sha256` and media ids), `image_sha256`, `warnings` (free text) or the trace's step text.
- `ReadOutputSchema` gains the arm with `z.enum(DISH_KINDS)`, `z.enum(MEAL_FLUID_KINDS)`, `z.enum(PORTION_BASES)` and `z.union(PORTIONS.map(z.literal))`. The no-text test walks every string leaf against the vocabularies. A dish name in a `string` field fails to parse in tests before it can reach the table.
- Request counts are untouched. Recording is one SQLite insert after the model calls, so the tray read stays at 3, 5 or 1, as the budget allows.

### 2. Meal links (`src/routes/chart.ts`, HTTP; `src/chart/model-accuracy.ts`, domain; `src/store/store.ts`)

- `MealBody` gains `read_id: z.number().int().positive().optional()`. No `read_draft`: a tray read has at most one draft.
- **Order in the handler.** First the existing checks: the body, 404, `charted_at`, media, the evidence and photo-hash binding, and tray-comparison's served-photo rules. Then `linkProblem(store.read(read_id), store.linked(read_id, 0), ctx)`. Then `addMeal`.
- **`linkProblem` gains one row** in its kind table: read kind `tray` ↔ record `meal` ↔ source `photo`. A `manual` meal with `read_id` fails at the kind step. A `tray` read on an entry or level, or a `photo`, `text` or `voice` read on a meal, fails there too.
  - A tray read with 0 drafts (`not_a_meal` with nothing read) fails the draft step. The issue is reported at `read_id`, since meals have no `read_draft`.
  - The order and the messages are read-outcomes'. `already linked` stays the contract.
- **The insert.** `addMeal` takes an optional `readId` and inserts `read_link (read_id, 0, meal_id = the meal, linked_at)` inside its existing transaction, after the meal and its fluid entry. A primary-key conflict throws `ReadLinkTaken`, which rolls back the meal, its entry and its proof, and maps to the same 400.
  - The link names the meal, never its fluid entry, so the entry's own history (approval, amend, rejection) is read through the meal.
- A photo meal posted without evidence (its upload failed, so `saveMeal` dropped it) still links: the read happened and the meal was drafted from it.
- **The web (`lib/meals.ts`).** `saveMeal` decides once, at the first save attempt, whether the post carries `read_id`, through read-outcomes' `decideRead` margin and `trayDrafts(read.draft)`. It sends none when the read is stale or has 0 drafts ("Empty tray read"), so a meal charted by hand on the photo of an empty read is saved unlinked (201), and that read stays `negative_confirmed` (or `nothing_drafted`), as a no-draft photo read charted by hand does in read-outcomes.
  - **`already linked` on a retry.** When a retried meal post answers 400 with `{ path: "read_id", message: "already linked" }`, the earlier post reached the server and saved the meal. `saveMeal` then returns the save result from the posted input, and the form shows `saveMealText` of it, with no error, as the round does (read-outcomes' "Round saves resume after a failure"). `saveMealText` takes `Pick<Meal, 'meal' | 'portion' | 'fluid_ml'>` for that.

### 3. Meal outcomes (`src/chart/model-accuracy.ts`, pure)

`store.readOutcomeRows(since, wardId?)` gains, per meal link:
- the meal's `voided_at`, current `portion` and `dishes` (kinds and portions only), and `proof.confirmed` (portion, fluid mL, dishes);
- its `meal_event` amendments, before and after;
- its fluid entry's `status`, `recorded_ml`, `approved_ml`, current `volume_ml` and `amended` events.

Each tray draft linked to a meal gets one outcome. The first matching row wins. These rows slot into read-outcomes' table after its negative rows (1–7), which already cover unlinked drafts:

| # | Item | Condition | Outcome |
|---|---|---|---|
| M1 | meal of a negative read | voided | `negative_confirmed` |
| M2 | meal of a negative read | otherwise | `negative_overridden`, saved as `meal` |
| M3 | meal | voided | `rejected` |
| M4 | meal | fluid entry `pending` | `pending` |
| M5 | meal | a `meal_event` changed the portion or the dish multiset; or the fluid entry is `rejected`; or `approved_ml ≠ recorded_ml`; or an `amended` event has `from_ml ≠ to_ml` | `corrected_by_nurse` |
| M6 | meal | the saved portion, fluid mL or dish multiset differs from the draft's | `edited_at_capture` |
| M7 | meal | — | `accepted` |

- **Saved values.** These are `proof.confirmed` when the meal has a proof. Otherwise they are the first `meal_event`'s before-values, else the meal's current values.
- **Dish multiset.** The sorted list of `(dish_kind, portion)`. Names are not compared. An amendment that changes only `items`, or only a dish's name, changes no multiset and leaves the outcome ("Renamed only"). The requirement says "dish kinds or portions" for this: the meal portion and the multiset.
- **A rejected fluid entry on a standing meal is `corrected_by_nurse`, not `rejected`.** The meal stays charted, so the attendant's read of the tray stands. The nurse removed one value, the fluid, which is a correction of the draft. `rejected` is kept for the whole record being withdrawn (the void), as for entries. The fluid then counts as `removed` (§5).
- **Pending before corrected.** A meal whose fluid entry is unreviewed has no final fluid, exactly as a pending entry has no final value. A meal with no fluid has no entry and is settled at save.
- **Settled** meals (M5–M7) are scored by §4 and §5. Decided = settled + `rejected`, as for entries.

**Retaken tray reads** ("Retaken tray reads", MODIFIED "Unsaved drafts").
- **The rule.** An unlinked `tray` read with a draft is `retaken` when a later `tray` read has the same `staff_id` and the same non-null `admission_id`, and is at most `READ_RETAKE_MINUTES` after it. The later read's own outcome is unaffected: it may be linked, open, abandoned or retaken in turn.
- **No new field.** The next `/api/ai/meal` request names nothing: every tray read already stores `staff_id`, `admission_id` and `created_at` ("Tray reads are logged"), so the store derives the flag and no request or body changes.
- **No meal condition.** tray-comparison's "Retaken for another meal" retakes a compared lunch read as a snack. The attendant picked the wrong meal, not a second tray, so the first read is still superseded. A bed rarely gets two trays within 10 minutes, and a meal saved from the first read links it, which takes it out of the rule (unlinked only).
- **Store.** `readOutcomeRows` gains `retaken: boolean` per tray read, from one `EXISTS` over `model_read` (`kind = 'tray'`, same `staff_id` and `admission_id`, `id > r.id`, `created_at ≤ r.created_at + READ_RETAKE_MINUTES`). A read with a null `admission_id` never matches. No index or column is added; the read log is small and already filtered by window.
- **Precedence.** One row, R0, is placed before read-outcomes' unlinked rows (its design §4, rows 1–7): an unlinked tray draft whose read is `retaken` gets `retaken`, at once and for good. Then `open` under `READ_ABANDON_HOURS`, then `abandoned` or `negative_confirmed`. Linked drafts never reach R0. A read with 0 drafts has no draft to mark, so a `not_a_meal` read with nothing read stays `negative_confirmed` and a `tray_empty_unclear` one `nothing_drafted`.
- **Counting.** `retaken` is in `KindRow.outcomes` and `KindRow.drafts`, and in no decided count, no rate, no volume error, neither kept nor not kept, and no negative count. `Positives.retaken` counts the retaken drafts of reads that are not negative, so the kept line can name them.
- **Requests.** Outcomes are derived on each `GET /api/quality/model`, with 0 model requests. Each read in "Lunch read twice" made its own 3.

### 4. Dish pairing and portion agreement (`src/chart/scoring.ts`, pure)

```ts
interface DishFacts { dish_kind: DishKind | 'none'; portion: Portion | null }
/** Same kind first (each model dish takes the first unpaired final dish of its kind), then the rest in list order. Left-overs pair with 'none'. */
export function pairDishes(model: DishFacts[], final: DishFacts[]): { model: DishFacts | null; final: DishFacts | null }[]
/** |a − b| / 25 for each pair with both portions known. */
export function portionAgreement(pairs: { model: Portion | null; final: Portion | null }[], minN = MIN_N): PortionAgreement
export function topCorrections(classes: Record<ClassTable, ClassRow[]>, k = TOP_CORRECTIONS): TopCorrection[]
```

- **Why pair by kind, not by a per-dish identity on the meal post.**
  - The alternative was a `read_dishes` map sent with the meal (each saved dish's draft position), stored in a new `read_link` column. It needs a new body field, a migration, a MODIFIED "Dishes on a meal", and it breaks after a nurse amend, which replaces the dish list.
  - Pairing by kind needs no new field. It applies unchanged to the final dishes after an amend. It is the only pairing the lab can use, because model and truth come from different producers.
  - It differs from a true identity only among dishes of one kind, for example two `rice` dishes where staff removed the first: the portion pair may then match the wrong rice. The kind tally is unaffected. This is stated in Risks.
- **Tables.** Each pair becomes a `tallyClasses` row:
  - `model` is the drafted kind, or `none` for a dish staff added;
  - `final` is the kept kind, or `none` for a dish staff removed;
  - `settled` is true.

  The ward tallies `by: 'model'` and the lab `by: 'final'`, as for containers.
- **Portions.** `dish_portion` takes every pair with both portions known. `meal_portion` takes the draft's overall portion against the final meal portion. Rates use `rate()` (floored, null below `MIN_N`).
- **Measured portions.** A drafted dish's portion is tray-comparison's `portion`, which is `measured` when the served photo matched and Spark's otherwise. The ward scores what was drafted. The lab's per-basis split stays tray-comparison's.

### 5. Kind rates, meal fluid, container rows, positives, top corrections (`src/chart/model-accuracy.ts`, pure)

- **Kind rates.** Each `KindRow` gains `edited_at_capture` and `corrected_by_nurse`, from `rate(n, decided)` beside read-outcomes' `accepted`, `corrected` and `rejected` ("Rates per outcome"). The web's Table, popup and bar label read these rates as they come, so a figure on screen is always the server's floored, withheld-below-`MIN_N` value.
- **Meal fluid.**
  - The final fluid of a settled meal is its fluid entry's current `volume_ml` when the entry stands. It is none when the meal has no entry or the entry is rejected.
  - `summariseVolume` runs over the pairs with both values. `no_volume` counts no fluid drafted but one charted, and `removed` counts a fluid drafted but none charted.
  - The tray kind rows' `volume` is this score per mode. The top-level `volume` keeps read-outcomes' meaning (entries, levels and bag readings), so meal fluid never mixes with container volumes.
- **Container rows.**
  - They group photo reads, both modes, by `output.container`.
  - `reads` counts reads, `decided` counts their decided drafts, the rates are over `decided`, and `volume` is over settled drafts.
  - Sorted by `reads` descending, then `CONTAINER_KINDS` order.
  - Bag readings and jug levels count under their read's container. Negative reads are rows too (`none`, 0 decided), so the table shows where the model said "nothing here".
- **Positives.**
  - They cover every draft of a read with no `NEGATIVE_ISSUES` code, in every kind.
  - kept = accepted + edited_at_capture + corrected_by_nurse, and not kept = rejected + abandoned. Both rates are over kept + not kept.
  - `pending`, `open` and `retaken` drafts are outside, and so are `nothing_drafted` reads, which have no draft. `retaken` is counted apart, beside `rejected` and `abandoned`.
- **Top corrections.**

## Queued reads (read-queue, after this change)

read-queue (`openspec/changes/read-queue/`) is still being written and applies after this change (its proposal: … → accuracy-views → dietitian-care → scale-store → read-queue). As its proposal and design stand:

- **Tray reads are not queued** (its proposal, "Not queued"; its design §3.9). `/api/ai/meal` keeps acuity-budget's 429 and the by-hand meal form. So every tray read is synchronous: its row is written when `/meal` answers 200, and the meal form links it with `read_id` exactly as "Link a meal to its read" states. Nothing in this change's tray logging, meal links or meal outcomes depends on read-queue.
- **Queued reads are saved and linked by the server.** A queued photo, text or voice read that answers is logged then, and `saveRead` writes its records and their `read_link` rows in one store transaction, as the staff member who queued it and on its bed. read-outcomes' link checks hold by construction, and no web post carries its `read_id`. So read-queue modifies neither "Link checks" nor "Unsaved drafts", and the web's `decideRead` margin is not involved.
- **What read-queue MODIFIES:** read-outcomes' "Reads are logged" (a queued read is logged when it answers; one that fails, expires or is cancelled stores none) and "Outcome of a saved level" (a level or bag reading saved by a queued read counts in no number). Neither is a requirement this change modifies.
- **Effect on this change's numbers.** Container rows, positives and top corrections fold the same per-draft outcomes as the kind rows (§5). A draft that read-queue leaves out of `outcomes()` is therefore out of every one of them, which is what read-queue's design §9 asks of this change ("accuracy-views' summary must skip them"). read-queue's rule that a queued entry is never `edited_at_capture` flows through the same way.
- **Request counts are unchanged.** A tray read is 3, 5 or 1 requests, never queued and never retried, and the meal save and the summary make 0.

## Risks / Trade-offs

- **[Accepted is agreement, not truth]** A nurse who keeps a wrong portion makes it "accepted". → The README pairs ward numbers with the lab eval's labelled truth, now for trays too, and the corrected and not-kept rates are the conservative signal.
- **[Same-kind dish pairing can misattribute portions]** Two dishes of one kind, one removed, may pair the wrong portion (§4). → The kind tally is exact. The portion figure is labelled per pair count, and the Same-kind scenario pins the rule.
- **[A meal amend that only renames]** It changes no class, so it stays `accepted`. → Intended: names are free text and not scored.
- **[A rejected fluid counted as corrected]** A nurse rejecting a duplicate fluid entry on a correct meal reads as a correction of the draft. → It is one: the draft's fluid was not kept. The `removed` count shows it apart.
- **[Meal fluid pending for hours]** Newest meals stay `pending` until the round approves their fluid. → `pending` is outside every rate, as for entries, and meals with no fluid settle at once.
- **[Colours]** Two slots are below 3:1 on white. → The validator's relief rule is met by the legend, the popup, the printed accepted rate and the seven-column table. Status colours are never used.
- **[A tap opening nothing]** Base UI's Tooltip ignores taps, so a tooltip design would hide the four values from every phone user. → Each row is a Popover trigger, which opens on a tap, a click, Enter or a mouse hover. The browser check taps it at 390 px.
- **[Two trays within 10 minutes]** A second tray read for the same bed by the same staff within `READ_RETAKE_MINUTES` marks an unsaved first read `retaken`, even if it was a different tray. → Rare (one tray per meal per bed), and a saved first read is linked and never marked. The window is a named constant.
- **[Photo reads are not marked]** Photo reads keep read-outcomes' rules: the same staff and bed within 10 minutes may be a different container (a urinal, then the water jug), so an unsaved first photo read still becomes `abandoned` (proposal, Out of scope).
- **[Six kinds and seven columns at 390 px]** → Empty kinds are hidden, labels stack above the bars, and the table scrolls inside its wrapper with its first column sticky (read-outcomes).
- **[Tray eval overlap]** tray-comparison's tray eval could score differently from the ward. → §9: this change MODIFIES its "Tray eval report" word for word plus one rule, and makes the eval call the ward's functions. Task 0.2 re-copies the archived text.
- **[DESIGN.md §7.3 disagrees on the chart form]** A reviewer holding §7.3 would flag the stacked bars. → §7, step 1, records the decision, and task 7.7 rewrites §7.3 in the same change, so the file and the code agree at merge.
- **[read-queue is still being written]** It could later queue tray reads, or change how queued reads link. → "Queued reads" records its current shape (no tray reads; server-side links). It applies after this change, so any change to tray reads or meal links would be its own MODIFIED delta of this change's requirements.

## Migration Plan

1. No schema change, so no `STORE_SCHEMA_VERSION` bump: it stays 5 (bag-alerts). If the live `STORE_SCHEMA_VERSION` is not 5 at apply time, stop: changes were applied out of order. `read_link.meal_id` exists (read-outcomes), and its CHECK already allows a meal link.
2. Deploy server and web together. A new web's `read_id` on a meal post would get 400 from an older server, whose `MealBody` is strict.
3. Older meals have no link and count in nothing. Tray reads appear in the summary from the first read after deploy.
4. Rollback: run the previous build on the same file, which it opens because `STORE_SCHEMA_VERSION` is unchanged (fresh-schema). Meal links are ignored by read-outcomes' code, which reads only entry and level links, so they stay until this build runs again.
