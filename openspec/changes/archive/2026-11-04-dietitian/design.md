# Design

## Context

Motivation is in proposal.md, under "Why". This is the MVP cut; "Deferred" below lists what was taken out. The current state that shapes the approach:

- **Roles.**
  - `STAFF_ROLES` is `attendant`, `nurse`, `matron`. Policy reads three lists in `packages/shared`:
    - `DECIDER_ROLES`: approve, reject, amend and void;
    - `IN_CHARGE_ROLES`: may be named in charge;
    - `OVERSEER_ROLES`: not in a ward team; assign beds on their wards.
  - The web keeps exhaustive `Record<StaffRole, …>` maps (`ROLE_LABEL`, `ROLE_AVATAR`, `LANDING` in `apps/web/src/lib/staff.ts`), so adding a role is a compile error until each map has it. `LANDING`'s type is `'/a' | '/n'`, and TanStack Router types `navigate({ to })`, so `'/d'` needs a route file.
- **Teams.**
  - `staff_ward` rows hold each person's wards, rank 0 being the home ward. The matron has rank-0 rows but no home ward.
  - Four places say "not an overseer":
    - `orderTeam` drops overseers from `GET /api/wards/:id/team` (`apps/server/src/chart/staffing.ts:10`);
    - a demo account's `ward` is null for overseers (`apps/server/src/routes/session.ts:28`);
    - `demo-history.ts` finds a ward's team the same way (`teamOf`, `:324`);
    - the web's `DEMO_ACCOUNTS` fixture checks `role === 'matron'` (`apps/web/src/lib/staff-fixtures.ts:31-32`).
- **Store opening.**
  - `openStore` (fresh-schema) refuses a file at another `PRAGMA user_version`, creates `SCHEMA` in an empty file, then runs `seedStaff` → `seed` → `seedTeams`. There is no upgrade step.
  - The staff table's role CHECK is generated from `STAFF_ROLES` in `SCHEMA`, so adding a role changes `SCHEMA` and bumps `STORE_SCHEMA_VERSION` (1 → 2, with the `referral` table).
  - `seedStaff` (`store.ts:1855`) inserts missing demo staff by id (`ON CONFLICT (id) DO NOTHING`), and sets credentials only where `password_hash IS NULL`.
  - `seedTeams` (`store.ts:1875`) writes demo teams only into an **empty** `staff_ward`: "a store is never re-teamed". A fresh store's `staff_ward` is empty, so it gets every demo team, Sana Mirza's included.
- **Demo passwords.** `DEMO_PASSWORD_HASHES` (`src/store/demo-passwords.ts`) is generated by `scripts/demo-passwords.ts`, which today rehashes every member with a new salt. `verifyCredentials` (`auth.ts:83`) refuses a demo password with demo sign-in off by comparing the stored hash with the committed one, so the committed hashes of existing members must never change.
- **Apply order.** care-plan → bag-emptying → tray-segmentation → read-outcomes → dietitian: this change applies last, on the archived text and code of the other four ("Overlaps").
- **Care plan** (change `care-plan`; archived first). `chartView` (`chart/view.ts`) is the single composition point for chart reads, `beds_with_alerts` and Explain. It reads the bed's care orders in the window, and today reads meals only for beds with nil by mouth (`view.ts:26`). `withChart` (`routes/chart.ts`) reads a ward's orders in one query.
- **Alerts** (`chart/alerts.ts`). `logging_gap` needs the bed admitted at least `loggingGapH` (3 h) ago and `low_urine_output` at least `lowOutputWindowH` (6 h) ago. So on a fresh store opened at 07:00, no bed raises either before 10:00, which is how care-plan's "Only a catheter review" isolates one prompt.
- **Explain** (`routes/ai.ts:100`). It answers 409 `no_alerts` with no request when `chartView` gives no alerts, else sends one Spark request. `explainContext` (`ai/explain.ts`) holds the bed, weight, totals, alerts and entry lines; no patient name, no meal items.
- **Meals.** `GET /api/admissions/:id/meals` returns 24 h, and the bed review lists them ("Meals on the bed review"). A meal's fluid is `fluid_ml`; a snack's demo fluid is tea.
- **Reads and writes.**
  - GETs are open (`session` middleware passes GET and HEAD), and every non-GET needs a session.
  - Ward access is a web gate (`AccessGate`, `useNeedsReason`). The server does not check wards on writes ("Enforcing wards on writes" is out of scope in ward-staffing).

What it means for the design:
- **A meal-count trigger is a product heuristic, not a guideline.** No NHS, BDA or NICE source found states one of the form "half or less for N meals"; every policy read uses MUST plus a 3-day food chart. So `poor_meal_intake` is an early nudge to review, worded `Review.` and configurable. The README says so.
- **The ward-cover model matches practice.** A dietitian is allocated to wards (CUH), and referral by any nurse through the record is the norm (CUH, Leicestershire). Assigning a named dietitian to a patient covers specialist cases, such as a renal dietitian on a medical ward; that is deferred, so the MVP routes to the ward's dietitians only.
- **Dietitians close the loop with an outcome**, and the food chart is their evidence (Salisbury, NHS Borders). Hence `REFERRAL_OUTCOMES` and `next_review`. The MVP's evidence is the bed review's 24 h meals.

## Goals / Non-Goals

**Goals:**
- Role policy only through shared role lists. No role string in new server or web code.
- Zero new requests on any existing screen. Zero model requests, except the one Explain request a newly explainable bed can now make.
- With no dietitian on the roster, the app behaves exactly as today, apart from the new prompt.
- A store file from before this change fails to open (charting/entries "Store schema version"); it is never upgraded.

**Non-Goals:**
- A general referral or tasks engine. Referrals are dietetic only.
- A per-ward on/off switch. Availability comes from the roster.
- Nutrient analysis of trays.
- Anything under "Deferred".

## Deferred

Cut for the deadline. Each is a follow-up change; none is specified or built here.

- **Care plan:** the `diet` care kind and every care-plan delta (the MODIFIED Care order values, Care orders need a nurse and Care status on chart reads; the ADDED Diet order and Diet targets need a dietitian). `diet` is not added to `CARE_KINDS`, no care-plan registry changes, `CARE_ORDER_ROLES`, `DIET_TYPES`, `IDDSI_FOOD_LEVELS` and the target ranges are not added, and `requireDecider` stays on the care routes.
- **Assignment:** Assign a dietitian, the `admission_dietitian` table, `NutritionStatus.dietitian`, `mayAssignDietitian`, and `EntryList.in_charge`.
- **Reads:** Referral history and Patient nutrition read (`GET /api/admissions/:id/nutrition`, `NutritionView`, `DIETITIAN_WORKLIST_DAYS`).
- **Web:** Assign a dietitian from the bed review, Diet order on the care plan, Diet badges; and all of `web/dietitian` except the worklist: `/d/$id`, its referral, diet and assignment actions, break-the-glass there, and the "Your patients" and "Diet orders" sections.
- **tray-segmentation:** no `dishLines`, no dish list, no overlay. The Nutrition section shows the existing 24 h meals.
- **Demo:** HDU-3 renal diet, 5B-6 soft diet, 2C-3 assignment and closed referral.

## Decisions

### 1. The role and its lists

- `dietitian` is added to `STAFF_ROLES` and to no existing list. So `DECIDER_ROLES` keeps nurse and matron, and a dietitian gets 403 on review, amend and void through the existing `requireDecider`. `IN_CHARGE_ROLES` and `OVERSEER_ROLES` stay as they are.
- **`TEAM_ROLES` replaces "not an overseer"** in `orderTeam`, `session.ts`, `teamOf` (`demo-history.ts:324`) and the web's `DEMO_ACCOUNTS` fixture. The question at each place is "is this person on the nursing team?". A positive list answers it safely for any future role, which a growing "not X or Y" filter would not. For the existing roles the behaviour is identical.
- **New lists:** `DIETITIAN_ROLES` and `REFERRER_ROLES`. Every new check reads one of them; no role string is compared.
- **Alternatives considered:**
  - Making dietitians overseers. They would gain bed assignment, which is wrong.
  - A `can: Record<StaffRole, Permission[]>` matrix. It is a bigger refactor than the hackathon needs.

### 2. Routing to the ward's dietitians

- **Availability:** `ward_id ∈ coveredWards`. The covered wards come from one query: `staff_ward` joined to `staff` where the role is in `DIETITIAN_ROLES`, with the SQL `IN (…)` list built from the shared list, as `staffDdl` builds its CHECK.
- **Routing is computed at read time** from the dietitians' current `wards`, not frozen on the referral. A roster change moves open referrals with no data change.
- A named dietitian per patient is deferred. Since the worklist only lists referrals on wards in the dietitian's own `wards`, opening a row never needs break-the-glass; a dietitian covering every demo ward never sees the dialog.

### 3. The `poor_meal_intake` rule

`poorMealIntake(meals, now, { nilByMouth, orders, latestReferral })` lives in `apps/server/src/chart/nutrition.ts` (domain, pure):

1. If nil by mouth is active, or `latestReferral` is open or acknowledged, there is no prompt.
2. The meals counted are those:
   - not voided;
   - charted at or after `now − POOR_INTAKE_WINDOW_H`;
   - charted strictly **after** `latestReferral.closed_at` when the latest referral is closed (a meal at the same instant does not count);
   - not charted while a `nil_by_mouth` order was in force, from its start included to its end excluded, using the orders in the window as care-plan's "Entries judged by the order then in force" does;
   - not a drink-only snack: `meal === 'snack' && portion === 0 && fluid_ml > 0`.

   They are sorted by charted time, then id.
3. Take the last `POOR_INTAKE_MEALS`. If there are that many and each `portion ≤ POOR_INTAKE_PORTION`, raise the prompt with the message `Poor meal intake: the last <n> meals were <p>% eaten or less (<meal> <portion>%, …). Review.`, oldest first and in lower case.

- **"Latest N", not "any run in the window".** One good meal clears the prompt. It is about now, as the bed review's meal list is.
- **Window 24 h.** The bed review lists exactly the last 24 h of meals, so a nurse can see every meal the prompt names. A meal not charted is not counted as refused (proposal.md, "Out of scope").
- **Snacks count.** The food chart records every eating opportunity, and a meal-kind filter would make the demo and the rule depend on the time of day. A drink-only snack is a cup of tea, not a refused meal, so it is left out rather than counted as 0%.
- **Held while nil by mouth**, as care-plan holds `intake_target_behind`. Refused trays while fasting are expected. A meal charted while the order was in force is left out even after the order ends, so a lifted fast does not prompt from the fasting trays.
- **Held while referred, and restarted after the close.** This is the "instead of re-prompting" behaviour without a dismissal mechanism. The bed shows the referral chip instead. A close as "monitoring" does not re-prompt from the same meals, nor from one charted at the instant of the close.
- **Not a record kind.** It carries no `meal_ids`, so the `Alert` union and the record badges are unchanged.
- **Wiring.** `chartView` appends it last: after the care prompts and after bag-emptying's bag prompts, matching `ALERT_KINDS`. It now reads meals for every bed, through `store.meals(id, since)`, plus the latest referral and the covered wards. `withChart` reads a ward's meals, latest referrals and the covered wards in one query each (`store.mealsByWard`, `store.latestReferralsByWard`, `store.coveredWards`).
- **`WardReads`, a shared edit with bag-emptying.** After bag-emptying, `withChart` already passes the ward's care orders (`careOrdersByWard`) and bag readings (`bagReadingsByWard`) to `chartView`. This change gathers all five ward reads into one `WardReads` object (in `chart/view.ts`), keeping bag-emptying's reads as they are, so the ward list stays a constant number of queries per ward. `chartView` with no `WardReads` reads one bed, as today.
- **Explain.** Explain reads `chartView`, so a bed whose only prompt is `poor_meal_intake` now gets 200 and exactly 1 Spark request instead of 409 `no_alerts`. The message names meal kinds and portions only. `explainContext` is unchanged: no patient name, and no meal items (meals without a fluid add no entry line; a meal's fluid entry line has no items).
- **Fresh-store isolation** for the HTTP scenario "Counted on the ward list": the store is opened at 07:00, the meals are charted 08:00 to 09:00 and the read is at 09:30, 2.5 h after admission. `logging_gap` (3 h) and `low_urine_output` (6 h) cannot fire on any bed, no bed has orders, so `poor_meal_intake` on 3A bed 6 is the only prompt in the hospital.

### 4. Referrals: data model and state machine

```sql
CREATE TABLE IF NOT EXISTS referral (
  id INTEGER PRIMARY KEY,
  admission_id INTEGER NOT NULL REFERENCES admission(id),
  reason TEXT NOT NULL,
  note TEXT CHECK (note IS NULL OR length(note) BETWEEN 1 AND 200),
  created_at INTEGER NOT NULL,
  created_by INTEGER REFERENCES staff(id),
  acknowledged_at INTEGER,
  acknowledged_by INTEGER REFERENCES staff(id),
  closed_at INTEGER,
  closed_by INTEGER REFERENCES staff(id),
  outcome TEXT,
  next_review TEXT, -- local date YYYY-MM-DD
  CHECK ((closed_at IS NULL) = (outcome IS NULL)),
  CHECK (acknowledged_at IS NULL OR acknowledged_at >= created_at),
  CHECK (closed_at IS NULL OR closed_at >= created_at)
) STRICT;
-- One referral in progress per admission.
CREATE UNIQUE INDEX IF NOT EXISTS referral_in_progress ON referral (admission_id) WHERE closed_at IS NULL;
CREATE INDEX IF NOT EXISTS referral_admission ON referral (admission_id, created_at);
```

```
            refer (REFERRER_ROLES; a dietitian covers the ward; none in progress)
  (none) ───────────────────────────────────────────────────────────▶ open
  open ──── acknowledge (DIETITIAN_ROLES) ──────────────────────────▶ acknowledged
  open | acknowledged ──── close (DIETITIAN_ROLES; outcome, next_review?) ──▶ closed
  closed: final. A new referral may be made; the old row stays.
```

- **Status is derived**: `closed_at` → closed, else `acknowledged_at` → acknowledged, else open. No status column can drift.
- **One row per referral, with a column pair per step**, is the audit trail: who and when for each transition. A step only fills NULL columns, through a guarded `UPDATE … WHERE id = ? AND closed_at IS NULL [AND acknowledged_at IS NULL] RETURNING *`. There are no edits or deletes, so no separate events table is needed, as for `care_order`.
- **No CHECK on `reason` or `outcome`.** The route validates against the shared enums, so adding a value needs no table rebuild (the stance care-plan took on `kind`).
- **Note** (decided): optional, trimmed, 1–200 characters (`REFERRAL_NOTE_MAX`).
  - The reason enum carries the routing meaning. The note covers what an enum cannot ("asks for vegetarian meals"), as `REJECT_REASONS` with its 200-character note does today.
  - It is stored and shown to staff. It is never logged, never in an error message, and never sent to a model (Explain gets only alerts and entry lines).
- **The race on refer.** Availability and "none in progress" are checked in `tx()`. The partial unique index turns a lost race into 409 `referral_open`.

### 5. HTTP

New `nutritionRoutes(store)` in `apps/server/src/routes/nutrition.ts` (HTTP only), mounted beside `careRoutes` behind the app-level `session` and `sameSite` guards. The chains below are the spec's error order.

| Route | Chain | Answers |
|---|---|---|
| `POST /admissions/:id/referrals` | `requireRole(REFERRER_ROLES)` → admission → `smallJson` → `ReferralBody` → covered → in progress | 403 · 404 · 413 · 400 · 409 `no_dietitian` · 409 `referral_open` · 201 `Referral` |
| `POST /referrals/:id/acknowledge` | `requireRole(DIETITIAN_ROLES)` → referral lookup → guarded update | 403 · 404 · 409 `not_open` · 200 |
| `POST /referrals/:id/close` | `requireRole(DIETITIAN_ROLES)` → referral lookup → `smallJson` → `CloseBody` → guarded update | 403 · 404 · 413 · 400 · 409 `already_closed` · 200 |
| `GET /nutrition/worklist` | session staff or 401 → `requireRole(DIETITIAN_ROLES)` | 401 · 403 · 200 `NutritionWorklist` |

- `requireRole(list)` generalises `requireDecider` (`routes/common.ts`), which becomes `requireRole(DECIDER_ROLES)`.
- **Close looks the referral up before the body**, so an unknown id gets 404 even with an invalid body ("Unknown referral before the body"), as care-plan's "Unknown admission before the body" does. The guarded update then decides 409.
- `CloseBody.next_review` is `z.iso.date()`, refined to `localDate(now) ≤ d ≤ localDate(now) + REFERRAL_REVIEW_MAX_DAYS`, compared as local calendar dates.
- **The worklist** reads the signed-in dietitian's `wards`, the in-progress referrals on those wards (one query, then one admission read per referral), and the meals of the last `POOR_INTAKE_WINDOW_H` (one query over all wards, filtered to the dietitian's beds; one dietitian covers every ward today). `worklistFor(staff, …)` (pure) orders open referrals by `created_at`, then acknowledged ones by `created_at`, ties by referral id. At 21 beds this is trivial.
- **The worklist GET needs a session and the role** because its answer is "for the signed-in dietitian". Another role gets 403, not an empty list, so a wrong landing is visible.
- Logs carry paths, statuses and timings only, never a note, reason or outcome.

- **Ward access stays a web gate.** The bed review `/n/$id` (unchanged) sits inside `AccessGate`. The server does not check wards on these writes, consistent with ward-staffing.

### 7. Web

- **`lib/nutrition.ts`** (DOM-free; every web scenario tests it):
  - label maps: `REFERRAL_REASON_LABEL`, `REFERRAL_OUTCOME_LABEL`;
  - lines and chips: `dietitianLine(n, wardName)`, `referralLines(r, now)`, `referralChip(n)`;
  - who sees what: `canRefer(staff, n)`, `canActOnReferral(staff)`, `isDietitian(staff)`;
  - the worklist: `worklistRows`, `intakeLine`;
  - request bodies and bounds: `referBody`, `closeBody`, `reviewBounds(now)`.

  Times use `HH:MM`, prefixed `D Mon` off today, as care-plan formats them.
- **`lib/labels.ts`:** `ALERT_LABEL.poor_meal_intake = 'Poor meal intake'` and `ALERT_TONE.poor_meal_intake = 'warn'`.
- **`lib/resolve-rules.ts`:** `REFER_PROMPTS = ['poor_meal_intake']` and `offersReferral(kind)`.
- **`lib/staff.ts`:**
  - `ROLE_LABEL.dietitian = 'Dietitian'`;
  - `ROLE_AVATAR.dietitian = 'in'` (the intake tint), widening its type;

## Risks / Trade-offs

- [The 3-meal trigger has no guideline behind it (see Research)] → It is worded `Review.`, configurable, held while referred, and the README says it is a nudge, not a screen.
- [Explain can now spend one request on a bed it used to refuse] → Still one request per tap, as for every other prompt; the input has no name or meal items.
- [Every bed now reads its meals for the prompt] → One meals query per ward list, and one per bed read. That is fine at 21 beds. Index `meal (admission_id, created_at)` already exists.
- [Snacks count towards the run] → Documented, and drink-only snacks are left out. A `POOR_INTAKE_MEAL_KINDS` filter is a one-line follow-up.
- [Routing follows the current `wards`] → A roster change moves open referrals. That is intended. The referral row keeps who acknowledged it.
- [A regenerated demo password file reopens the production hole] → The script keeps committed hashes, and `git diff` of `demo-passwords.ts` shows one added line.
- [Rolling back] → The previous build refuses this store version (§8). Demo stores can be recreated.
- [A clinical misreading] → No prompt diagnoses. "Not a diagnostic device" stays in the README.
